# 开源 README 模式笔记

这些是选择信息组织方式的参考，不是可复制的模板。先按**读者要做什么**和**仓库扮演什么角色**选取相应模式，而不是按技术关键词找同类项目。

## 命令行工具

- [`uv`](https://github.com/astral-sh/uv)：首段定位产品，安装方式按平台分开；每个主要能力都以命令和真实终端结果证明，详细主题导向独立文档。
- [`bat`](https://github.com/sharkdp/bat)：先用真实界面展示核心感知价值，再给最常用命令；平台安装说明旁放置实际差异，例如特定发行版中可执行文件名称不同。

适用判断：用户需要立刻在本机使用工具。优先写“用什么命令、看见什么、在什么系统上有什么例外”，而不是先写完整参数字典。

## 开发者库

- [`HTTPX`](https://github.com/encode/httpx)：一句话说明定位，随后给安装、最小调用和真实响应；可选功能的额外依赖在使用它之前说明。

适用判断：读者要把能力嵌入自己的代码。首个示例必须涵盖导入、调用和返回值，输入限制、版本支持和可选组件不能放在不相关的章节。

## 框架与服务

- [`FastAPI`](https://github.com/fastapi/fastapi)：通过“创建代码 -> 启动服务 -> 打开 URL 检查响应”构成完整首次闭环；更深的异步、CLI 和部署说明下沉到文档。

适用判断：用户在仓库能力之上建立新东西。不要只给安装或代码片段，必须解释如何确认已成功运行。

## 面向最终用户的自托管产品

- [`Immich`](https://github.com/immich-app/immich)：首屏用真实产品截图说明用户将得到什么，直接链接安装文档和 Demo；涉及用户资产时，把备份提醒放在开始操作之前。

适用判断：读者主要是使用、部署或评估产品。真实界面、演示入口、安装文档与风险提示比开发目录更重要。

## 平台与大型源码仓库

- [`Supabase`](https://github.com/supabase/supabase)：先说明平台价值和可用能力，然后分流到完整文档、开发入口与架构解释；不会把整个平台的使用手册复制进 README。
- [`VS Code`](https://github.com/microsoft/vscode)：明确区分开源源码仓库与面向普通用户发布的产品，把下载、贡献、反馈和源码构建分别指向正确入口。

适用判断：仓库不是读者唯一入口，或同时面对用户、贡献者和维护者。README 的职责是正确分流，而非让所有读者执行同一条安装命令。

## 插件、扩展与集成

- [`Obsidian Sample Plugin`](https://github.com/obsidianmd/obsidian-sample-plugin)：明确宿主 API 与可见能力，开发路径从放入插件目录、编译、重载到启用；发布流程单独下沉。

适用判断：项目只能在某个宿主或外部系统中发挥作用。README 应优先说明宿主版本、安装位置、权限或凭据边界，以及启用后的可见结果；不要把主项目的全量安装步骤复制进来。若集成会调用外部 API、读取用户数据或产生费用，相关条件必须出现在配置动作之前。

## 数据集、模型与研究复现

- [`Sentence Transformers`](https://github.com/UKPLab/sentence-transformers)：先给安装与可观察的模型输出，再按模型任务和训练/评测主题链接到深层文档；研究型软件的引用和实验性质也明确写出。

适用判断：读者要下载、加载、评估或复现实验，而非运行一个通用应用。先写来源、许可证、任务定义和适用范围；随后给出数据格式、最小加载或推理/复现实验。指标必须同时包含数据划分、评测条件和版本等上下文，限制、偏差与不适用情形不可隐藏在末尾。

## 模板、脚手架与示例项目

- [`Cookiecutter`](https://github.com/cookiecutter/cookiecutter)：把“使用模板生成项目”和“制作模板”分为不同读者路径，展示生成命令及产物来自何处。

适用判断：读者要从此仓库派生新项目。README 需要清楚给出创建或复制路径、生成后得到的内容、主要修改点、环境变量和部署前提。模板维护者的构建、测试和发布流程应下沉到贡献文档，避免阻断使用者。

## 文档、规范与资源集合

- [`Awesome-Selfhosted`](https://github.com/awesome-selfhosted/awesome-selfhosted)：先界定收录范围与排除项，把超长列表作为可导航索引，并提供更合适的 HTML 浏览入口。
- [`Docusaurus`](https://github.com/facebook/docusaurus)：将文档站的开始路径和技术文档分开，使仓库 README 保持为入口而不是重复完整站点内容。
- [GitHub README 指南](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)：将 README 定位为“项目做什么、为何有用、怎样开始、去哪里求助”的入口，并建议把长文档下沉。

适用判断：项目本身是信息、规则或导航。优先帮助读者找到正确内容并理解覆盖范围、版本与维护方式，不要让 README 重复整个文档站或目录树。

## 公开协作项目的补充

[Open Source Guides](https://opensource.guide/starting-a-project/) 把 README、许可证、贡献指南和行为准则视作不同职责的文件。README 应链接到协作规则并说明维护状态、贡献预期或“不接受贡献”等边界；它不是替代这些文件的地方。

## 反模式

- 用某个领域的 README 当作所有项目的默认结构。
- 首屏是徽章、愿景、技术栈或泛化特性，却没有读者能实际完成的动作。
- 有命令却没有真实输出、URL、响应或结果解释。
- 用户产品没有真实体验证据，或用装饰图片冒充功能证明。
- 把所有平台的安装命令混在一起，却不说明差异和已知限制。
- 把源码仓库、发布产品、在线文档和贡献入口混为一谈。
- 插件不写宿主版本、权限或配置位置；数据和模型不写来源、许可证或评测条件。
- 把模板维护者流程、数据集制作流程或文档站全文放入使用者的首次路径。
- 先罗列所有参数、目录、架构，再给第一次成功路径。
- 将假设中的能力、未验证的性能或未来计划写成当前事实。
- 把同类开源项目的标题、段落和目录原样移植，忽略当前项目规模和受众。
